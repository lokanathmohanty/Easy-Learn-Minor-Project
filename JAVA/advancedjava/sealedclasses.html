Java - Sealed Classes and Interfaces (Java 17+)

Introduction to Sealed Types

Sealed Classes and Interfaces, made standard in **Java 17**, provide a powerful mechanism for controlling **inheritance**. They allow a class or interface (the *sealed type*) to explicitly declare which other classes or interfaces (the *permitted subtypes*) are allowed to directly extend or implement it.

This feature enables developers to create a **finite, determinable, and explicit hierarchy** of types, which is useful for scenarios like pattern matching (e.g., with switch expressions) where knowing all possible subtypes upfront is beneficial.

Declaration Syntax

A type is sealed using the sealed keyword, followed by the permits keyword to list the allowed subtypes.

// Sealed Class Example
public abstract sealed class Shape permits Circle, Square, Triangle {}

// Sealed Interface Example
public sealed interface Service permits API, DatabaseAccess {}

Constraints on Permitted Subtypes

Any class or interface that directly extends or implements a sealed type must satisfy two main constraints:

  1. Location: The permitted subtype must be in the **same module** as the sealed type (or in the same package if residing in the unnamed module).
  2. Required Modifier: Every permitted subtype must be explicitly declared using one of three modifiers:
    • final: The inheritance chain stops here. This subtype cannot be extended further.
    • sealed: The subtype itself is sealed, continuing the restriction but allowing its own further controlled inheritance.
    • non-sealed: The restriction is removed. This subtype is now open to being extended by any other class, just like a regular class.

Example of Permitted Subtype Modifiers

abstract sealed class Person permits Employee, Manager {}

// 1. Final: Stops the hierarchy
final class Manager extends Person {}

// 2. Non-sealed: Opens the hierarchy back up
non-sealed class Employee extends Person {}

Benefit: Exhaustive Switch Expressions

One of the primary uses of sealed types is enabling the compiler to check for exhaustiveness in switch expressions, meaning you don't need a default case if you cover all permitted subtypes.

public static int getId(Person person) {
    return switch (person) {
        // Compiler knows these are the ONLY two possibilities because Person is sealed
        case Employee emp -> emp.getEmployeeId();
        case Manager mgr -> mgr.getManagerId();
        // default case is optional IF all sealed permits are covered
    };
}
