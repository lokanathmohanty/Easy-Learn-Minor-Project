Garbage Collection (GC) in .NET Core

The **Garbage Collector (GC)** is a core feature of the .NET managed code platform that acts as an **automatic memory manager**. It handles the **allocation and release of memory** for objects, freeing the developer from manual memory management.

Content: Overview and Process

An allocation occurs when you declare an object using the new keyword or when a value type is **boxed**. Allocations are generally fast.

The process of **garbage collection** occurs when there isn't enough memory to allocate a new object. The GC must then **collect and dispose of 'garbage' memory** (objects no longer in use) to make space available for new allocations.

Advantages of Garbage Collection

  • Developers **don't need to manually free memory**.
  • Allocates objects efficiently on the **managed heap**.
  • Reclaims memory from unused objects, keeping it available for future allocations.
  • Provides memory safety by preventing one object from using the content of another.

Conditions for GC Triggering

Garbage collection runs automatically when one of the following conditions is met:

  1. The system has **low physical memory**.
  2. The memory used by objects on the managed heap **surpasses an acceptable threshold**.
  3. The GC.Collect method is explicitly called (rarely needed; mainly for unique situations or testing).

Example: Generational Garbage Collection

The .NET GC uses a **generational approach** based on the principle that most objects are either **short-lived** or **long-lived**. There are three main generations, plus a special heap for large objects:

Generation 0 (Gen 0)

  • **First allocation space.** New objects are created here.
  • Objects are typically **short-lived** and are often collected before the next GC cycle.
  • The heap is **small**, making collections very quick.

Generation 1 (Gen 1)

  • Objects that survive a Generation 0 collection are **promoted** here.
  • Acts as a **second chance space** for short-lived objects.
  • Heap is also **small**, and collections are quick.

Generation 2 (Gen 2)

  • Contains all **long-lived objects** (survived Gen 1 collection).
  • This heap can grow to be **very large** (e.g., 10s of GBs in server programs).
  • Collections can take noticeable time, but the GC uses techniques like **background threads** to minimize blocking program execution.

Large Object Heap (LOH)

  • A separate, dedicated heap.
  • Reserved for objects that are **85,000 bytes or greater**.
  • Large objects are allocated **directly** to the LOH, bypassing the generational heaps.
  • Collections on the LOH are tied to Generation 2 collections.
