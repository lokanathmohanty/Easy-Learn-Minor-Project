Java - Garbage Collection (GC)

What is Java Garbage Collection?

Garbage Collection (GC) is the automatic process managed by the **Java Virtual Machine (JVM)** that automatically reclaims memory occupied by objects that are no longer reachable (in use) by the application. This eliminates the need for manual memory deallocation (unlike C or C++) and prevents memory-related errors like **dangling references**.

The GC's primary activities include:

  • Finding and identifying unused (dead) objects.
  • Freeing the memory they occupy in the heap.
  • **Coalescing** (or compacting) the remaining live objects to combine small fragments of free memory into larger contiguous blocks, thereby preventing **memory fragmentation**.

A major challenge in GC is the **"stop-the-world" (STW)** pause, where application threads must be stopped while the GC is running, especially when objects are moved (compacted). Minimizing the frequency and duration of these pauses is the goal of GC tuning.

Generational Heap Design

Most modern JVMs divide the heap memory into generations based on the observed lifespan of objects, which drastically improves GC efficiency. These generations are:

  • Young Generation (YG): Holds newly created, typically **short-lived objects**. It is usually small and collected frequently.
    • The YG is further divided into an **Eden space** (where new objects are initially allocated) and two **Survivor spaces**.
  • Old Generation (OG): Holds **long-lived objects** that have survived multiple collections in the Young Generation (a process called "tenuring"). It is larger and collected less frequently.

Types of Garbage Collection

  • Minor GC: Occurs when the Young Generation fills up. It is typically fast because the YG is small. Dead objects are discarded, and live objects are promoted to a Survivor space or the Old Generation. Minor GC always causes a short STW pause.
  • Full GC: Occurs when the Old Generation fills up or when the Metaspace/PermGen is resized. Full GC involves collecting and compacting the entire heap (both YG and OG). This can result in long STW pauses, making it the primary target for optimization.

Common Garbage Collectors

Modern JVMs offer various collectors designed to prioritize different goals (throughput vs. latency):

  • **Serial Collector**
  • **Throughput Collector (Parallel)**
  • **CMS Collector (Concurrent Mark Sweep)**
  • **G1 Collector (Garbage-First)** (Default in recent JDKs)
  • **ZGC (Z Garbage Collector)** and **Shenandoah** (Low-latency, concurrent GCs)

Tuning Garbage Collectors

Tuning the GC involves configuring memory allocation to balance the frequency and duration of GC pauses with the application's overall throughput.

1. Heap Size Allocation

The key is to avoid memory requests that force the operating system into using **swap space** (virtual memory backed by disk), which drastically slows down the application and GC. The recommended rule is to never request more memory than the **physical RAM** available.

  • -XmsN: Sets the **initial** heap size.
  • -XmxN: Sets the **maximum** heap size.

Setting -XmsN equal to -XmxN is often recommended if the application's memory needs are known, as it prevents the JVM from needing to dynamically resize the heap at runtime, which improves GC efficiency.

2. Generation Sizes Allocation

This affects the trade-off between Minor and Full GC frequency.

  • -XX:NewRatio=N: Sets the ratio of the Old Generation to the Young Generation (Default is 2, meaning OG is 2/3 and YG is 1/3 of the total heap).
  • -XmnN: Explicitly sets the size of the Young Generation (-XX:NewSize=N and -XX:MaxNewSize=N). A larger YG means fewer Minor GCs but longer Minor GC pauses.

3. Permagen and Metaspace Configurations

This area holds class metadata used by the compiler and runtime:

  • **Java 7 and earlier:** Called **Permagen**. Size controlled by -XX:PermSize=N and -XX:MaxPermSize=N.
  • **Java 8 and later:** Called **Metaspace**. Size controlled by -XX:MetaspaceSize=N (initial size) and -XX:MaxMetaspaceSize=N (maximum size).

Unlike Permagen, Metaspace can occupy unlimited native memory by default (if MaxMetaspaceSize isn't set), which can lead to OutOfMemory errors. Increasing the initial Metaspace size is often recommended for large applications to prevent frequent resizing and subsequent Full GCs during startup.
