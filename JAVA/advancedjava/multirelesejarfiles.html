Java Multi-Release JAR Files (Java 9+)

What is a Multi-Release JAR (MRJAR)?

The **Multi-Release JAR (MRJAR)** feature, introduced in **Java 9**, allows a single JAR file to contain different versions of the same classes or resources, each targeted at a specific major Java release (e.g., Java 9, 11, 17, etc.).

Why MRJARs Were Introduced

MRJARs solve the problem of third-party library and framework developers having to maintain **multiple separate source code bases** just to support both older and newer versions of the Java platform. It acts as a bridge, allowing libraries to:

  • **Adopt New Features:** Utilize modern Java features (like interfaces with private methods or new APIs) for newer JREs.
  • **Maintain Backward Compatibility:** Ensure the library still functions correctly on older JREs (like Java 8) that don't support the new language features.
  • **Reduce Duplication:** Keep all versions of the code for a library consolidated in a single file, simplifying maintenance and distribution.

MRJAR Structure and Loading Mechanism

An MRJAR has a specific directory structure that the Java Runtime Environment (JRE) uses to select the appropriate class files.

Key Components

  • **Root Directory (Base Version):** Contains the **least common denominator** version of the classes and resources (e.g., the Java 8 or Java 7 version). This is the version loaded by any JRE that does not support the MRJAR feature or is older than the oldest specified version.
  • **MANIFEST.MF Entry:** The file must contain the entry Multi-Release: true in its main section to signal to the JRE that it is an MRJAR.
  • **Versioned Directories:** Specific versions of classes are placed inside the META-INF/versions/ subdirectory, using the major version number as the folder name.

    Example structure:

    jar root/
   - Calculator.class  (Base JRE version)
   META-INF/
      - versions/
         - 9/
            - Calculator.class (Java 9 specific)
         - 11/
            - Calculator.class (Java 11 specific)

Class Loading Logic

When an MRJAR is executed, the JRE follows this logic:

  1. If the JRE **does not support** MRJARs (e.g., Java 8 or earlier), it **ignores** the META-INF/versions/ directory and loads only the classes from the **root directory**.
  2. If the JRE **supports** MRJARs (Java 9+), it determines its own version (e.g., Java 11).
  3. It searches for the **highest versioned directory** that is less than or equal to its current JRE version (e.g., a Java 11 JRE would pick classes from the 9/ and 11/ folders over the root).
  4. If a class is found in the specific version folder (e.g., META-INF/versions/11/Calculator.class), that version is loaded.
  5. If a class is **not** found in the version folder, the JRE falls back and loads the class from the **root directory**.

**Important Constraint:** To ensure proper function, the **public interface** (method signatures, visibility) of all versioned classes must remain **identical** to the base class.
