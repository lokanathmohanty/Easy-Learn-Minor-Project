Java Platform Module System (JPMS) - Java 9+

What is the Java Module System?

The **Java Platform Module System (JPMS)**, introduced in **Java 9**, fundamentally changes how Java code is organized and packaged. A **Module** is a new programming component and an abstraction layer above a package.

It is a **self-describing collection of code and data** that defines what it needs (dependencies) and what it makes available (exports). This system is designed to improve encapsulation, security, reliability, and performance by addressing the long-standing "JAR hell" and classpath issues.

The Java platform itself is modularized, as seen by the command java --list-modules, which shows many individual modules like java.base, java.desktop, and java.xml.

Core Principles of Modularity

A module enforces two critical concepts:

  1. Strong Encapsulation: By default, all packages within a module are **not visible** to the outside world. A package must be **explicitly exported** to be public. This prevents unauthorized access to internal implementation details, even public classes, which was a weakness of the old classpath system.
  2. Reliable Configuration: A module explicitly declares its dependencies using the requires directive. The Java Runtime Environment (JRE) can verify that all necessary modules are present at link time or run time, leading to more reliable applications (no more "missing dependency" errors at runtime).

Declaring a Module: module-info.java

Every custom module is defined by a **module descriptor** file named **module-info.java** located at the root of the module's source folder. This file contains all the metadata about the module.

Key Directives (Module Declarations)

  • module my.module { }

    The basic declaration, assigning a unique name to the module.

  • requires other.module;

    Declares a **mandatory dependency**. This module cannot compile or run without other.module being available.

  • requires transitive other.module;

    Declares a dependency that is also exposed to any module that depends on *this* module. If module A requires transitive module B, and module C requires module A, then module C implicitly requires module B.

  • requires static optional.module;

    Declares an **optional (compile-time) dependency**. The module is needed for compilation but is optional at runtime. It's often used when a module might not be present on the target JRE.

  • exports com.mypackage.api;

    Makes the **public types** (classes, interfaces) in the specified package accessible to **all** other modules that require this module.

  • opens com.mypackage.internal;

    Allows the package's contents to be accessed by **reflection** at runtime, which is sometimes necessary for frameworks (like Spring or Hibernate) that inspect code dynamically. It bypasses strong encapsulation for that package.

New Development Features

  • Modular JARs: A standard JAR file that includes a module-info.class file in its root.
  • JMOD Format: A new packaging format, similar to JAR, that can also contain native code, configuration files, and other non-Java resources, mainly used by the platform itself.
  • jlink Tool: A new tool that allows developers to assemble a specific set of modules to create a **custom, optimized JRE runtime image** that contains only the components needed for the application. This drastically reduces the size of deployment bundles.
