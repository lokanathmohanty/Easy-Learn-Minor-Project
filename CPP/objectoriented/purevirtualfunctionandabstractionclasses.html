C++ Abstract Classes and Pure Virtual Functions 🧱

**Abstract classes** and **pure virtual functions** form the mechanism in C++ for defining an **interface** or contract that derived classes must implement. This is a crucial tool for achieving full polymorphism and flexible system design.

Pure Virtual Functions

A **pure virtual function** is a virtual function declared in a base class that is explicitly marked as having **no implementation** in the base class. It serves as a placeholder to be defined by derived classes.

Declaration

A pure virtual function is defined by placing **= 0** after the function signature:

class Base {
public:
   // Pure virtual function
   virtual int calculateArea() = 0; 
   // ... other members
};

The = 0 is a specific syntax used only for this purpose and does not represent an assignment of the value zero.

Abstract Classes (Interfaces)

A class that contains **one or more pure virtual functions** is automatically considered an **Abstract Base Class (ABC)**. The core rules for ABCs are:

  • **No Instantiation:** You **cannot create objects** directly from an abstract class (e.g., Base b; is illegal). An ABC serves only as a blueprint for inheritance.
  • **Implementation Requirement:** Any derived class that intends to be a **concrete class** (a class you can instantiate) **must override and implement every pure virtual function** inherited from the ABC.
  • **Inheriting Abstract Status:** If a derived class fails to implement all inherited pure virtual functions, that derived class also becomes an **abstract class**.

Enforcing the Interface Contract

The primary role of an abstract class is to **enforce an interface contract** on all its derived types. For example, if Shape is abstract with a pure virtual getArea(), every class derived from Shape (like Rectangle or Circle) is **forced** by the compiler to define its own getArea() method.

This ensures consistency when objects are treated polymorphically via a base class pointer.

// Base class pointer
Shape* shapePtr; 

// The compiler knows shapePtr->calculateArea() MUST exist,
// even though it doesn't know *how* it's calculated.
